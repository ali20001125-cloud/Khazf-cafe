# كاشير خزف

نظام كاشير مقهى + ولاء. **مشروع منفصل تماماً عن موقع خزف.**
Next.js + Neon Postgres · عربي · RTL.

المواصفات في `docs/CAFE-POS-LOGIC.md` (منطق العمل) و `docs/CAFE-POS-PLAN.md` (الخلفية)
والقرارات المحسومة في `docs/DECISIONS.md`.

---

## الحالة: المرحلة ١ مكتملة، وقاعدة البيانات حيّة

| | |
|---|---|
| ✅ المشروبات | إضافة/تعديل/تعطيل · فئة · سعر · محصول · مؤهّل للولاء |
| ✅ المواد الخام | غرام / مل / حبة · مخزون · حد تنبيه |
| ✅ الوصفات | مادة + كمية لكل مشروب · «للسفري فقط» للكوب والغطاء |
| ✅ شاشة البيع | شبكة كبيرة · سفري/جلوس · شوت إضافي · سلة |
| ✅ الدفع | كاش (مبلغ مستلم + باقي) · بطاقة (زرّ فقط، بلا بوابة دفع) |
| ✅ الفاتورة | طباعة حرارية ٨٠مم من المتصفح |
| ✅ خصم المخزون | تلقائي وذرّي عند كل بيع مدفوع |

**المراحل القادمة:** ٢ الجرد (يومي وأسبوعي وشهري) والفرق والهدر · ٣ الموظفون والورديات والدرج والتقرير الاستثنائي · ٤ الولاء · ٥ التحليلات.
جداول كل المراحل موجودة في المخطّط من الآن حتى لا نكسره لاحقاً.

## قاعدة البيانات

**Neon Postgres 17 · مشروع `khazf-cafe` · فرانكفورت `aws-eu-central-1`.**
منفصل تماماً عن قاعدة متجر خزف الأونلاين.

المخطّط والدالة والبذور **مطبَّقة فعلاً** على المشروع الحيّ:
١٤ جدولاً · دالة `checkout` · ١١ إعداداً · ٦ مواد · ١١ مشروباً · ٣٨ سطر وصفة.

لإعادة البناء من الصفر على قاعدة جديدة، شغّل بالترتيب:

1. `db/migrations/0001_init.sql` — الجداول والأنواع
2. `db/migrations/0002_checkout.sql` — دالة إتمام البيع
3. `db/seed.sql` — منيو ومواد ووصفات مبدئية

## الأمان

- **لا واجهة قاعدة بيانات عامة.** Neon يعطي رابط اتصال فقط، بلا REST مكشوف
  وبلا مفتاح مجهول يعيش في متصفح الزبون. مساحة الهجوم أصغر بكثير.
- `src/lib/db.ts` معلَّم `server-only` — استيراده في مكوّن متصفح **يفشل البناء**.
- **الأسعار تُحسب داخل قاعدة البيانات**، لا من المتصفح. لو عبث أحد بالطلب المرسل،
  السعر يبقى سعر الجدول.
- البيع **عملية ذرّية واحدة**: الطلب والبنود وخصم المخزون معاً، أو لا شيء.
  مُتحقَّق منه فعلياً: محاولة بمبلغ ناقص لم تترك طلباً ولا حرّكت مخزوناً.
- **أرقام الفواتير بلا فجوات**: الرقم يُسحب بعد نجاح كل التحقّق، فالمحاولة الفاشلة
  لا تحرق رقماً. أي فجوة لاحقاً تعني شيئاً يستحق السؤال.
- **كل Server Action يفحص صلاحيته بنفسه.** فحص الـ layout وحده لا يكفي:
  الـ Server Actions تُنادى بطلب مباشر لا يمرّ على شجرة الصفحات.
- كل المدخلات تُنظَّف على الخادم: معرّفات UUID، حدود الكميات، قوائم بيضاء
  للفئات والوحدات ومفاتيح الإعدادات.
- تعديل الأسعار والوصفات يُسجَّل في `audit_log`.
- **زرّ «بطاقة» يسجّل فقط** — لا بوابة دفع ولا بيانات بطاقات في النظام.

**لماذا لا RLS؟** كانت ضرورية على Supabase لأن مفتاح `anon` منشور بالمتصفح ويصل
لقاعدة البيانات مباشرة. على Neon لا يوجد دور عام أصلاً، فتفعيلها بلا سياسات
كان سيقفل التطبيق عن جداوله بلا أن يمنع أحداً. الحماية هنا: الرابط سرّ خادمي.

افتراضات مبدئية، تُعدَّل كلها من `/admin/settings` أو محرّر الوصفات بلا نشر كود.
التفاصيل في `docs/DECISIONS.md`.

## الطباعة

الفاتورة تُطبع من المتصفح على حرارية ٨٠مم عبر `@page { size: 80mm auto }`،
وتُفتح نافذة الطباعة تلقائياً بعد كل بيع.

**عند شراء الطابعة:** اضبطها طابعة افتراضية وفعّل الطباعة الصامتة
(في Chrome: `--kiosk-printing`) حتى تخرج الفاتورة بلا نافذة تأكيد.

---

## النشر

الكاشير غير منشور بعد. للنشر على Vercel: اربط المستودع واضبط `DATABASE_URL`
و `ADMIN_PIN` كمتغيّرَي بيئة خادميّين، ثم بدّل أسعار المنيو من `/admin/drinks`.

**قبل التشغيل على فلوس حقيقية:** لم تُبنَ بعدُ الورديات ولا الجرد ولا الإلغاء
ولا الإرجاع. شغّله بالتوازي مع طريقتك الحالية حتى تكتمل المرحلتان ٢ و٣.
